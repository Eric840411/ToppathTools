## 24. OSM UAT 整合測試 — Backend 分頁改走 Agent 派工（2026-08-21，v4.23.0）

**路由**：`/api/osm-uat/*`｜**page key**：`osm-uat`

### 執行架構
Playwright 從「server 本機 spawn」改成「派工給 Local Agent」（跟 AutoSpin 的 A2、scripted-bet 同一套）。**server 只負責建 session、挑 agent、把 log 轉進既有的 SSE**，真正的 Chromium 跑在 agent 端。伺服器端 spawn 保留當 fallback，所以公網（Spug）上不需要裝瀏覽器。

| 模式 | 觸發 | 行為 |
|------|------|------|
| `agent` | 有可用 agent（自動挑）或前端指名 `agentId` | 送 `backend_uat_start`，agent 端 spawn `run-lark-tc-backend.js` |
| `server` | 前端明確選「伺服器端（fallback）」，或沒指名且一台可用 agent 都沒有 | 舊行為，本機 spawn |

**指名了卻挑不到一律 409，不默默 fallback**——否則使用者以為跑在自己機器上，實際在公網主機偷偷開了一顆 Chromium。

### WS 訊息（4 支）
| 訊息 | 方向 | 內容 |
|------|------|------|
| `backend_uat_start` | server → agent | `sessionId`／Lark appToken+tableId／`filter`／`dashGameType`／`dashClientVersion`／`modulePlan`／`credEnv` |
| `backend_uat_log` | agent → server | `sessionId`／`line`／`stream`（stdout｜stderr），逐行轉發 |
| `backend_uat_done` | agent → server | `sessionId`／`exitCode`／`error?` |
| `backend_uat_stop` | server → agent | `sessionId` |

`osm-uat.ts` 掛在 **worker process**（見 `server/worker.ts`），跟 `/ws/agent` 是同一個 process，所以直接拿 `agentConnections` 發訊息，不用再跨 process 轉一手。

### 把 API 變成斷言：`assert_api_called`（v4.46.0）

錄製畫面的 API 清單每一列可以點，直接產生一顆斷言積木。只「看得到」的話，使用者還是得自己把「這支 API 應該回 200」翻譯成積木——中間那段轉換正是不熟的人卡住的地方。

**比對用 `urlPattern` 不是原始網址**，`*` 是唯一的萬用字元、其餘字元全部逸出（使用者填的是字面字串，不該被自己網址裡的 `.` 或 `?` 咬到）。

**點過來時的預設值刻意分兩種**：錄到 2xx → 設成「要 2xx」；錄到非 2xx → 固定成當下那個碼。後者使用者要的多半是「這裡本來就會這樣」或「這裡不該錯」，兩種都得先看到實際的碼才好決定，預設成 2xx 等於幫他猜。

**⚠️ `netMark` 一定要設在 `openPath` 之前**：`openPath` 會等到 networkidle 才回來，設在它後面的話頁面載入時打的 API 全部落在界線之前，這顆斷言會**永遠看到 0 支**。而「開這頁時打了哪些後端」正是最常要驗的東西。實測才發現——單元測試是直接餵假資料進 `ctx.netCallsSince`，蓋不到這段。

**runner 的 `netCallsSince(ts)` 一定要用時間界線切**：`netCapture` 是整輪共用的（掛在同一個 page 上），不切的話問的會變成「整輪跑下來有沒有出現過」，那幾乎永遠是 true，等於沒驗。

### 錄製期間顯示打到的 API（v4.45.0）

錄製只錄得到 DOM 操作。但使用者要決定「這一步該下什麼 pass/fail」時，最需要知道的其實是它打了哪些後端——**很多成功／失敗根本不在 DOM，在 API 有沒有送出、回什麼碼**。看不到 API 的話，錄出來的斷言只能停在「畫面上有這個字」那一層。

agent 端 `page.on('requestfinished')` → `backend_record_net` → server 收進 session → `/record/status` 回傳 → 錄製狀態列下方即時列出。**只送 xhr／fetch**：一頁動輒上百個圖檔與靜態資源，全送會把 WS 洗爆，而且對「要驗什麼」沒有幫助。

**URL 一定要 pattern 化**（`toUrlPattern()`，放在 `net-capture.js` 讓兩邊共用一份規則）：錄下來的是當下那一次的網址，裡面常有 id／token／時間戳。之後要把某筆 API 變成斷言時如果直接拿原始網址當條件，**錄完當天可以跑、隔天全紅**——最難查的那種壞法。收斂規則保守：拿掉整段 query、路徑裡純數字／uuid／長 hex 換成 `*`，其餘原樣。**原始網址一起留著**，pattern 是額外欄位不是取代（CodeX review 要求：資料模型一開始就要能轉斷言）。

**`/ws/agent` 的註冊訊息是 `agent_ready` + `operatorKey` + `agentToken`**，不是 `register` + `ownerKey` + `token`。照直覺猜的話 server 會靜默拒絕，只回「目前沒有連線中的 Local Agent」，完全看不出是註冊格式錯了。檢查腳本見 `scripts/ui-checks/uat-record-network.mjs`。

### UI 檢查腳本：導頁一定要先點群組再點子項

`scripts/ui-checks/uat-subtype-modal.mjs`。這個 app **沒有 URL 路由**，頁面是純 React state——直接 `goto` 某個網址或直接點「UAT 整合測試」都到不了，因為子項在群組展開之前根本還沒 render。要先點「OSM Tools」再點子項。**我在這上面連續卡了三次驗證**才發現，之前那幾次「進不到 UAT 頁面」的結論全部作廢重來。

腳本裡也會量彈框尺寸：這個版面的祖先有 `backdrop-filter`，會把 `position: fixed` 困在容器裡，沒用 portal 的彈框會被裁掉（積木編輯器與錄製選擇器都踩過）。**量到滿版才代表 portal 有效**——這是唯一能實際證明 portal 必要性的方法，光讀 CSS 看不出來。

### 停止：runner 一定要自己接 SIGTERM

`chromium.launch()` **預設會註冊 `handleSIGTERM`** 去關瀏覽器。node 收到 SIGTERM 的預設行為是直接結束，但**只要有人註冊了 listener，那個預設就沒了**——於是瀏覽器被關掉、腳本卻還活著繼續跑下一筆 TC，每一筆都噴 `Target page, context or browser has been closed`。使用者看到的就是「按了停止還在跑」（2026-08-24 回報）。

修法兩層，缺一不可：

1. **runner**：`launch()` 帶 `handleSIGTERM/SIGINT/SIGHUP: false` 把 Playwright 的訊號處理關掉，自己接一份——關瀏覽器、3 秒逾時保險、明確 `process.exit(130)`。按第二次直接退出。
2. **agent**：送出 SIGTERM 後起一個 8 秒計時，還沒結束就 `SIGKILL`。單筆 TC 可以跑好幾分鐘，訊號也可能被某個函式庫攔走；沒有這個升級，「停止」會變成「看起來停了但其實還在跑」。

**⚠️ 這條在 Windows 上測不出來**：Windows 的 `child.kill('SIGTERM')` 不是真的送訊號，Node 直接強制終止程序，listener 根本不會執行（實測確認：註冊了 listener 的子程序仍然回 `signal=SIGTERM`、handler 沒印任何東西）。也就是說 Windows 上「停止」本來就會立刻生效，這個 bug 只在 macOS／Linux 的 agent 上出得來。要驗這條必須在 macOS agent 上跑。

### 幾個容易踩的邊界
- **停止要分支**：agent 模式送 `backend_uat_stop` 之後**不在當下收尾**，等 agent 回 `backend_uat_done` 才算真的停（才拿得到真實 exit code）；agent 已離線才直接標記。fallback 模式才 kill 本機 child。兩邊不共用同一套 kill 假設。
- **agent 斷線要優先攔截**：Backend UAT 的 `sessionId` 是 UUID、沒有 `sb_` 前綴，不先在 worker 的 close handler 攔下來，會掉進既有的機測分支誤呼叫 `cancelDistSession` 並廣播機測錯誤。`handleBackendUatAgentDisconnect()` 回傳 boolean 就是給 worker 判斷「這輪我處理掉了」。
- **H5/PC 那條線的斷線收尾（2026-09-18，v4.166.0）**：`worker.ts` 的 close handler 原本只收 Backend 的三條，H5/PC 的 `uatAgentSessions`／`uatRunSessions` 完全沒收。留下的殘骸是安靜的——錄製 session 永遠 `done:false`（將來拿它當鎖讀就會鎖死一台 Agent，症狀長得像「使用者自己在忙」）、run 的 DB `result` 永遠停在 `running`。
  現在 `handleUatRecordAgentDisconnect()` / `handleUatRunAgentDisconnect()` 收尾，兩件事要一起做對：**標成「中斷」而不是「完成」**（只設 `done` 的話前端會顯示「錄製完成」），**而且不刪 session**——已錄到的積木要留著讓人取回（`docs/decisions.md`：斷線不代表停止）。run 的 DB 收尾帶 `AND result='running'`，使用者自己按停止的那筆不該被斷線改寫成失敗。檢查：`scripts/ui-checks/uat-record-disconnect.mjs`。
- **`isSessionAlive()` 兩種模式分開判斷**：server 模式看 child 的 `exitCode`，agent 模式看該 agent 的 WS 還開著沒。只看 `session.status` 的話，agent 拔網路線會把使用者永久鎖在 409。
- **腳本的 cwd 一定要是 `server/uat-runner/`**：`run-lark-tc-backend.js` 用相對路徑讀 `./tc-registry.json` 和 `./config/*`。

### H5/PC 的選擇器階梯（2026-09-18，v4.167.0）

**原本 H5/PC 錄製器只有 `cssPath` 一種選擇器**——正是 Backend 五階階梯裡最脆的那一階。
H5 是 Vue 3：scoped style 產生的 `data-v-xxxxxxx` 是雜湊、class 大量是編譯產物，
純結構路徑一改版就全紅。跟後台當初被 Element UI 動態 class 咬的是**同一個病**。

階梯抽到 `server/uat-runner/selector-ladder.js`，Backend 與 H5/PC 共用：

| | 共用層 | adapter |
|---|---|---|
| 穩定屬性／label／表格列錨點／穩定祖先／可見文字／結構路徑 | ✅ | |
| Element UI 的 form-item、下拉面板、`.el-menu-item` | | 只給 Backend |

**切法是「DOM／Canvas 能力」不是「平台」**（CodeX 2026-09-17 定）：點在 `<canvas>` 上錄座標，
點在真 DOM 上走階梯。所以 PC（Cocos）的外層大廳 DOM 也吃得到階梯，H5 若嵌了 canvas 也會自動退回座標。

**錄製當下的驗證在兩邊是不同的東西**：Backend 有 Playwright（`verifyRecordedSelectorLive`），
H5/PC 走原始 CDP、**沒有 page 物件**。定案是「只驗語意對得齊的原生 CSS，其他回 `unknown` +
`unsupported`，**不另寫一份 Playwright selector 的 matcher**」——仿一份出來就是同一條規則兩份實作，
漂掉的症狀是「錄的時候說沒問題、跑起來找不到」。

⚠️ **合法 CSS 也不代表兩端等價**：Playwright 的 CSS 會穿透 open shadow DOM、原生
`querySelectorAll` 不會。元素不在主 document 樹上一律 `unknown`，否則會拿「原生查不到」
去宣告「選擇器壞了」。（實務上 document 層的監聽器收到的 target 已經被重新指向 host，
所以錄到的是 host——那是驗得到的元素。）

**重播也要走同一支解析**：`createRecordedLocators(page, { requireUnique: true })`。
直接 `page.locator()` 的話 `label=` 會被當成未知引擎拋錯，而且命中多筆會安靜取第一個。

**順手修掉的三個既有問題**（都不會報錯）：
1. 兩個 host 的 H5 錄製器**早就漂了**：agent 錄 `click`/`fill`、伺服器錄 `click_viewport`/`type`。
   而 `fill` 在伺服器模式的引擎裡不存在 → 「不支援的動作 → **skipped**」，腳本照樣 PASS。
2. 伺服器模式的去重用整段錄製共用的 Set → **同一顆按鈕按第二次安靜消失**。
3. 本機錄製的 Chrome 仍用亂數 CDP port（v4.165.0 改了 agent 端三處，漏了這處）。

檢查：`scripts/ui-checks/h5-selector-ladder.mjs`（接線）、
`server/uat-runner/frontend-recorder.browser-test.mjs`（真的開 Chrome 用原始 CDP 點下去）。

**CodeX 覆核補的兩項（v4.168.0）——兩個都是「看起來已經做對了」的陷阱：**

1. **shadow DOM 的來源要用 `composedPath()[0]` 判斷，不能只看 `event.target`。**
   target 跨出 shadow 邊界會被重新指向 host，而 host 通常真的唯一命中 → 那一步被標成 `ok`。
   但 host 裡有兩顆按鈕時，重播點 host 的中心**不保證落在原本那一顆**。
   「不確定」被包裝成「已驗證」，而且重播不報錯。測試裡有一條用 Playwright 真的重播的證據。
2. **`recordedLocator()` 是「當下解析一次」，要給它 `resolveTimeoutMs`。**
   Playwright 的 `.click({ timeout })` 是**拿到 locator 之後**才開始等的；解析階段就拋，
   那 10 秒根本走不到。H5/PC 的元素幾乎都是非同步渲染的——接上共用解析反而**比舊寫法更早失敗**。
   重試的是解析，不是唯一性：期限內每次照樣要求唯一命中。Backend 維持預設 0（行為不變）。

### Agent 版本比對用原始碼指紋，不用版號（2026-09-02，v4.94.0）

**手動維護的版號一定會漂，而且這個專案有活證據**：`agent-runner.ts` 裡的
`AGENT_VERSION = '2026-05-agent-owner-v1'` **從 5 月起沒動過**，而 agent 的原始碼
這期間改了很多次。server 只是把它收進 `version` 顯示，拿它判斷新舊等於沒判斷。

改成比對「白名單那批原始碼的指紋」（`server/agent-source-hash.ts`）：改了就一定測得出來，
不需要任何人記得 bump。

**⚠️ 三個一定會踩的點：**

1. **指紋要對「實際 serve 出去的內容」算，不是對 repo 裡的原始檔。**
   `serveAgentSource()` 會把 `machine-test/runner.ts` 的 gemini import 改寫成 agent 專用版本
   ——照原始檔算的話 agent 的副本永遠對不上，會**固定顯示需要更新**（CodeX review 提醒）。
   所以 serve 跟 hash 共用 `agentSourceContent()`，不各寫一份。
2. **換行要正規化**（CRLF→LF，檔尾收斂成剛好一個 `
`，用 `
*$` 不是 `
+$`）。
   repo 在 Windows 上 checkout 是 CRLF、agent 可能是 macOS——不正規化就固定顯示需要更新。
3. **要排序後再算。**`Object.keys()` 的順序不保證跨版本穩定，順序一變指紋就變。

**三種狀態，因為下一步不一樣**（跟 CodeX 討論定案，不能合成一個「不是最新」）：

| 狀態 | 判斷 | 使用者要做什麼 |
|---|---|---|
| `needs_update` | agent 手上檔案指紋 ≠ server | 按「更新程式碼」 |
| `needs_restart` | 檔案已最新，但**啟動當下**那批要重啟的檔案指紋是舊的 | 重開 agent |
| `unknown` | 舊版 agent 沒回報指紋 | **不要當成最新**——那會讓真正落後的顯示正常 |

**⚠️ `RESTART_REQUIRED_SOURCES` 的判斷依據是「`agent-runner.ts` 有沒有靜態 import 它」**，
不是看檔名。`uat-runner/net-capture.js` 與 `pinus-probe.js` 最容易歸錯邊——名字在
`uat-runner/` 底下看起來像 runner 專用，但 `agent-runner.ts` 是**直接 import** 它們的
（H5/PC 派工要用），所以要重啟。反過來 `run-lark-tc-backend.js`／`toppath-agent.py`／
`block-engine.js` 是每次執行才 spawn，寫完下次跑就生效。

**⚠️ `update_sources` 完成後 agent 會回報新的 `sourceHash`，但刻意不更新 `bootRestartHash`**
——那個要重啟才會變，它正是「檔案新了但跑的是舊的」的判斷依據；在那裡跟著更新的話
「需要重啟」就永遠偵測不到。

> 已驗證 19 項（`scripts/ui-checks/agent-version-check.mjs`）：CRLF/LF 一致｜檔尾換行差異容忍｜
> 鍵順序無關｜少一個檔案測得出來｜三種狀態各自正確｜**沒回報指紋是 unknown 不是 current**｜
> 兩者都落後時先報 needs_update（更新完才知道要不要重啟）｜需重啟清單分類正確。
>
> ⚠️ **派工當下的警告還沒接**：`/api/autospin/hub-agents` 等派工用的端點各自獨立，
> 要逐支帶上 `updateStatus`。目前只有 Local Agent 頁會顯示。

## 25. UAT 網路載入量測與 pinus 攔截（2026-08-22，v4.24.0）

### 共用模組放在 `server/uat-runner/`，不是新開一個 TS 模組
三個啟動 Playwright 的地方執行方式各不相同：

| 位置 | 怎麼跑 |
|------|--------|
| `server/uat-runner/run-lark-tc-backend.js` | 純 node 直接 spawn（Backend 分頁）|
| `server/agent-runner.ts` | agent 端用 tsx 跑（H5/PC 派工）|
| `server/routes/frontend-auto.ts` | 編譯進 `dist-server`（H5/PC 伺服器端）|

**只有 `uat-runner/` 這個目錄會被 `scripts/build-server.cjs` 整包 `cpSync` 到 `dist-server`**，所以它是唯一一份原始碼三邊都載得到的位置。寫成 `.ts` 的話 Backend runner（純 node）載不了；寫在別的目錄的 `.js` 又不會被複製進 `dist-server`。型別給 TS 端用的宣告在隔壁 `net-capture.d.ts`（`include: ["server/**/*.ts"]` 會撿到它，`.d.ts` 不會被 emit）。

**兩個檔案都要在 `AGENT_SOURCE_WHITELIST` 裡**——三個 runner 都 import 它們，少送一個 agent 端會在 **import 當下**直接炸掉，不是執行到才失敗。

### 網路量測（`net-capture.js`，三個分頁都有）
資料一律取自 Playwright 的 `requestfinished` + `request.timing()`，**不注入頁面 JS**——時間由瀏覽器本身提供最準，也不會被遊戲自己的程式碼干擾。

**三種資料刻意排除在統計之外**（跟 CodeX 討論時他特別提的風險）：

| 排除項 | 為什麼 |
|--------|--------|
| `likelyCached` | 快取命中的圖看起來一定很快，但那不代表首次載入也快，混進平均值會讓問題被蓋掉 |
| `isRedirect` | redirect 每一跳都是獨立 request，不是使用者等待的實際內容 |
| `isPreflight` | 瀏覽器自己發的 `OPTIONS`，同上 |

**`likelyCached` 是推測不是事實**：Playwright 沒有暴露 `fromDiskCache`（那是 CDP `Network.responseReceived` 才有的欄位），這裡用「完全沒有建線階段 + 總時間 < 5ms」當訊號。欄位名稱刻意帶 `likely` 就是不要讓人把它當成確定的事。

**門檻用固定值不用相對統計**（API 2000ms／圖檔 1500ms／其他 3000ms，`UAT_NET_THRESHOLD_*` 環境變數可覆寫）：UAT 要的是「這次有沒有異常」的紅黃綠判斷，固定值好解釋、好調參；p95 那種相對基準在樣本少的時候會飄到不能用來判定。

**不逐筆回報**：一個遊戲頁動輒幾百張圖，逐筆丟進 SSE 會直接洗版。比照 AutoSpin `track_button_health()` 的做法——平常只累積，**只有超過門檻的才即時印出來**，收工時再出一次 summary。

### pinus 攔截（`pinus-probe.js`，只有 H5/PC）
Backend 測的是 CP／NC 後台管理站，那是一般網站沒有 pinus；掛上去也只是 `status().present === false`，不會壞事，所以三個 runner 用同一套接線不用特判。

**補丁一定要打在 prototype 上**，這點是 AutoSpin 從 v3.90.1 一路踩到 v3.90.12 才確定的（見上面 AutoSpin 章節）：熱更新或斷線重連時遊戲會建立**全新的** `window.pinus` 物件，補在舊 instance 上的東西完全無效。`patchMethod()` 沿 prototype chain 找到「實際定義這個方法的物件」補在那裡，補一次永久生效，之後所有共用同一個 prototype 的新 instance 自動繼承。**已用測試驗證過重連情境**（換一個新的 `Object.create(proto)` 之後補丁仍然攔得到）。

**訊息內容會裁形**（`safeShape()`，深度 3、陣列最多 10 筆、字串 200 字）：遊戲訊息裡可能有整份牌面／獎項表那種大陣列，完整保存會讓頁面記憶體爆掉、日誌也完全不能讀。

**要定期 `drain()`**（三個 runner 都設 3 秒一次）把頁面端 buffer 搬回 node 端，滿了就會開始丟訊息。**摘要一定要在關瀏覽器之前產出**——最後一批訊息還在頁面端 buffer 裡，等到 `finally` 時 page 已經沒了，那批會整批遺失。

| 看 pinus 訊息 | H5/PC 執行日誌收工時顯示，依 route 分組統計次數與往返時間 |

## 26. UAT 網路監測即時面板（2026-08-22，v4.25.0）

第 25 節的量測資料原本只寫進執行日誌，這節把它接成畫面。`NetworkPanel.tsx` 三個分頁共用——資料來源不同，但到了前端已經是同一個形狀，沒有理由做兩套 UI。

### 資料怎麼上來
| 分頁 | 路徑 |
|------|------|
| Backend | runner `console.log` 一行 `@@UAT_STATS@@{json}` → `osm-uat.ts` 的 `captureStatsLine()` 攔掉 → SSE `stats` event |
| H5/PC（agent）| `uat_run_event { kind: 'stats' }` → `worker.ts` 轉 `pushStats()` → SSE `stats` event |
| H5/PC（伺服器端）| 直接 `pushStats()` → SSE `stats` event |

**Backend 只有 stdout 一條通道**，所以結構化資料只能夾在 log 流裡用行前綴區分。`STATS_LINE_PREFIX` / `formatStatsLine()` / `parseStatsLine()` 都由 `net-capture.js` 統一提供——**印的端跟解析的端一定要共用同一個常數**，兩邊各寫一份字串的話，改了一邊沒改另一邊的症狀是「面板永遠不更新而且沒有任何錯誤訊息」。

**統計行要在 `appendLog()` 之前攔掉**：它是資料不是日誌，混進 `session.logs` 會把執行日誌洗版，而且面板也拿不到（面板聽的是另一個 event）。

### 兩個容易漏的細節
- **SSE 是「接上之後才收得到」**：中途才打開面板的人沒有初始快照就會空白到下一次 2 秒廣播。`osm-uat.ts` 存 `session.stats`、`frontend-auto.ts` 存 `statsSnapshots`，新連線時補送一次。
- **最後一份一定要單獨送**：定時廣播最多晚 2 秒，不補送的話面板會停在倒數第二筆，跟日誌裡的摘要對不起來。

### 畫面上的設計決定
- **嚴重度用左側色條而不只是數字變色**：一整排掃過去，形狀差異比色相更快被看到
- **p95 畫成「相對門檻」的位置條**：看條比看數字快，一眼知道離爆掉還有多遠；逼近 80% 就先示警，等真的超過才變色太晚
- **語意色（good/warn/bad）跟 `--uat-primary` 分開**：不然藍色同時代表品牌和某種狀態，掃一眼分不出哪個要處理
- **排除筆數做成帶提示的 chip**：不解釋的話使用者只會看到「擷取 381、統計 163」然後懷疑漏抓
- **pinus 區塊只在真的攔到訊息時才渲染**：Backend 沒有 pinus，永遠掛個空表格會讓人以為壞了
- **每次開跑前清空上一輪快照**：舊數字留在畫面上會被誤讀成這一輪的

### 訊源欄：路徑在上、主機在下（2026-09-02，v4.93.0）

**`commonOrigin()` 是全有全無，而真實資料剛好踩中。**它只在「全部列同源」時才把 origin
抽掉只留路徑；實測 21 筆裡 20 筆是同一個後台、1 筆是 `uat-cp` 的 challenge-platform，
於是**整個機制失效、每一列都退回完整網址被截成 `https://u…`**——整欄零資訊，要 hover

## 27. 後台測試積木化（2026-08-22，v4.26.0 起，分階段）

### 為什麼要做
原本一筆 TC 能設定的只有「要不要跑」，**不能改「跑的時候檢查什麼」**——`tc-registry.json` 只存 `verifierName`，實際邏輯是 23 支寫死在 `run-lark-tc-backend.js`（5000 行）的函式加一張 `SUBTYPE_MAP`。加一種檢查只能改那支腳本。

**終點是全部積木化**（使用者 2026-08-22 確認），不是兩套並存。所以 `verifierName` / `SUBTYPE_MAP` / `BUILTIN_VERIFIERS` 都是**遷移期的橋**，拆完要整段移除，不要在新功能上依賴它們。

### 第一階段（v4.26.0）：引擎
`server/uat-runner/block-engine.js`。registry 一筆 TC 多一個 `steps` 陣列，有就照積木跑、沒有走原路徑。**目前 0 筆 TC 帶 steps，所以行為完全沒變**，只是引擎換好了。

17 顆積木：開啟後台頁面／點擊／輸入文字／套用篩選／讀取色塊／讀取表格／欄位必須有值／兩值必須相等／排序必須正確／控制項必須存在／表格必須有這一欄／下拉選項數量／開對話框檢查欄位／不該出現／截圖／標記需人工／內建驗證器。每顆宣告 `params`（前端積木庫與參數表單直接讀 `BLOCK_DEFS`，**不要在前端另抄一份**——抄兩份的結果是「畫面上有這顆積木、跑起來說不認得」）與 `outputKind`/`inputKind`。

### 幾條在 review 中定下來、之後不要走回頭路的規則
- **`onFail: continue` 一樣算失敗**，只是繼續跑好把剩下的問題一次看完。第一版寫成「continue 不計入 criticalFails」，等於驗證失敗卻整筆 TC 顯示通過——**假通過比直接報錯還糟**（CodeX review 抓到）。三種模式的差別只在「要不要繼續」，不在「算不算失敗」。
- **`manual` 不是失敗**，它代表「這件事機器判不了」，不是「這件事錯了」。判定優先序：有 `criticalFails` → FAIL；否則有 `manual` → MANUAL；否則 PASS。
- **這五種一律 criticalFail 且中止，不受 `onFail` 影響**：引用不存在的變數、變數型別不符、變數重名（除非明確 `overwrite: true`）、缺必填參數、不認得的積木。這些都是「積木寫錯了」不是執行期狀況，讓它 continue 只會讓後面每步都失敗、噴一堆看不懂的訊息。**不認得的積木尤其不能靜默跳過**——那會讓沒跑到的檢查看起來通過。
- **`toNumber()` 取不到值回 `undefined` 不回 0**：回 0 會讓「沒抓到」跟「值就是 0」混在一起，比對時變成假通過。
- **容差沿用既有 `cmp()` 的規則**（相對誤差 + 絕對誤差至少容許 1），不要另創一套。

### 積木存哪裡：DB，不是 tc-registry.json（v4.27.0）
**這點踩過一次**：第一版讓編輯器寫回 `tc-registry.json`，API 回成功、讀回來也對，但實測發現寫進去的是 **`dist-server/server/uat-runner/tc-registry.json`**——runtime 的 `__dirname` 在 dist 底下。而 `scripts/build-server.cjs` 開頭就 `rmSync(outDir)`，**使用者編好的積木會在下一次 `npm run build` 無聲消失**。

現在的分工：
| 東西 | 存哪 | 誰寫 |
|------|------|------|
| `verifierName`／`canonicalText`／`matchedVia` | `tc-registry.json` | 出廠預設，唯讀 |
| 使用者編的 `steps` | DB `uat_tc_steps` | 編輯器 |

執行時 server 把 DB 積木包成 `UAT_TC_STEPS` 環境變數帶給 runner（跟 `UAT_MODULE_PLAN` 同一套），runner 疊回 `TC_REGISTRY` 上。**agent 派工也走這條**（塞進 `backend_uat_start` 的 `credEnv`），所以 agent 端不需要有任何積木檔案。

### 畫面（v4.27.0）
之前整個 UAT 畫面**沒有「單筆 TC」這一層**——模組只設定「要收哪些 TC」，`/api/osm-uat/scan` 也只回分類統計，積木沒有地方可以掛。現在 scan 多回逐筆 `tcs`，模組卡片的「N TC」可展開看到實際收到哪幾筆，點進去開積木編輯器。

- 編輯器放在**工作台下方的整寬區塊**，不放右側設定欄——那欄只有 280~320px，三欄編輯器塞不下
- 模組 → TC 的比對沿用 `moduleCounts` 那一套（`matchesBackendModule`，specific 優先、沒有才落到 `*`），**不要另寫一份**：兩份比對邏輯遲早漂移，症狀是「清單顯示 4 筆但實際跑了 5 筆」
- 積木庫與參數表單全部照後端回的 `BLOCK_DEFS` 自動長

### 回寫 Lark：PASS / FAIL 兩個勾選欄位（v4.44.0）

使用者 2026-08-24 在表上新增 `PASS`／`FAIL` 兩個**勾選**欄位（原本的 `UAT測試`／`PROD測試` 留著但程式不再寫入）。

**回寫的結果是三態不是布林**：`pass`／`fail`／`manual`／`none`。原本傳的是 `markPass = result.pass && !result.manual`，「失敗」跟「人工判讀」都被壓成 `false`——以前只勾一個欄位時看不出差別，要分別寫兩欄就必須分得出來。

**互斥要自己維護**：勾 PASS 的同時把 FAIL 清成 false，反之亦然。同一筆 TC 會重跑，上次 FAIL 這次 PASS 不清的話兩個框都是勾的。`manual` 兩個都清——機器判不了，既不是通過也不是失敗，留著上一輪的結果會讓人以為這次有驗過。

**回寫失敗以前只印 warning**。欄位型別一改就會出現「畫面全綠、Lark 上什麼都沒寫進去」而且沒人發現——最後那行漂亮的統計是這次跑出來的，跟表上有沒有更新是兩回事。現在失敗會印 ❌ 並在收工時再列一次。

### Lark TC 的欄位名是「任務」，不是「測試項目」

用真實資料（`data/raw/lark_tc_all.json`，134 筆）確認過的完整欄位清單：

```
PROD測試 | UAT測試 | UAT測試通過時間 | 任務 | 任務類型 | 任務子類型
创建日期 | 父記錄 | 父記錄 (1) | 父記錄 (1) (1) | 環境 | 編號 | 裝置 | 附圖 | 端口
```

### ⚠️ 表格錨點：`td:text-is()` 在 el-table 上永遠 0 個（v4.156.0）

使用者回報 EGM List 的第 4 步永遠失敗，訊息是「命中 0 個 · 不可見」，**加延遲一秒也一樣**。

舊錄製器的錨點是：

```
tr:has(td:text-is("4186-DFDC-9999")) > td:nth-of-type(17) button:nth-of-type(1)
```

Playwright 的 `:text-is()` 是**「最小元素」語意**——某個子元素也配得上那段文字時，父層就不算命中。而後台是 Element UI 的 el-table，**每一格的內容都包在 `<td><div class="cell">…</div></td>` 裡**，所以 `td:text-is()` 永遠配到那個 div、td 本身是 0 個。這不是等待問題，等多久都一樣。

實測（`scripts/ui-checks/recorded-selector.mjs`）：

| 格子長相 | `td:text-is()` | `:text-is()` |
|---|---|---|
| `<td>文字</td>` | 1 | 1 |
| `<td><a>文字</a></td>` | **0** | 1 |
| `<td><div>文字</div></td>` | **0** | 1 |

**同一支函式的第二個洞（CodeX 指出）**：按鈕序號用 `td.querySelectorAll(tag)` 算「這格裡第幾個後代」，卻產出 `nth-of-type`——那是「在自己父層裡同 tag 第幾個」。兩顆按鈕各自包在自己的 `<span>` 裡時，兩顆都是 `nth-of-type(1)`，選擇器會一次命中兩顆。

> ⚠️⚠️ **這裡也不能用 `:nth-match()`**（v4.156.0 第一版用了，v4.156.1 拿掉）。
> `:nth-match(sel, N)` 是從**整個查詢結果**取第 N 個，不是「在這一格裡取第 N 個」。
> 日後多出一列錨點文字相同、而且排在前面的列時，它會指到**別一列的按鈕**，
> **而且依然只命中 1 個**——「定位必須唯一」根本擋不住。實測：錄製時指 r1/b2，
> 前面插一列 r0 之後變成指 r0/b2，命中數還是 1。**安靜點錯比大聲失敗危險得多。**

現在的做法：格子裡只有一顆就用後代寫法（`td:nth-of-type(N) button`，最耐改版）；有好幾顆才改成**從 td 往下的相對結構路徑**。路徑只在這一格裡展開，列不唯一時整條選擇器會命中多筆而被擋下來。

**舊格式的辨識不能用字串替換**（CodeX P2）：`includes` + `split/join` 是子字串全域替換，**連引號裡的使用者資料也會被改**——機台名稱、備註那些值裡面出現什麼都不意外。現在逐字掃，只改落在引號外的結構部分；引號沒收尾的一律不採信、也不改。

**舊腳本的相容（跟 CodeX 討論定案）**：DB 裡存的原文一字不改，只在執行時由 `server/uat-runner/recorded-selector.js` 解析：

1. 先用原式。命中 1 個就用它，什麼都不做。
2. 只有「原式命中 0」且認得出是 `tr:has(td:text-is(` 這個固定形狀時，才試修正式。
3. 修正式**必須唯一命中**才套用；0 個或多筆一律不套，讓原本的錯誤照常拋出來。
4. 套用時 log 會印出原始與有效的 selector，不是靜默改掉。

> ⚠️ **不做全域字串替換**。`td:text-is(` 在別的位置可能是使用者自己寫的、有意義的寫法。
> ⚠️ **`recordedLocator()` 與 `checkLocator()` 必須共用同一支解析**——只修執行那邊的話，預檢仍會先用原式擋下來，等於沒修。

**固定欄副本與巢狀表格（v4.156.2 實測）**——驗收標準是**要麼命中原目標、要麼明確拒絕**，命中 1 個卻是別的元素絕對不允許：

| 情境 | 實測結果 |
|---|---|
| el-table 固定欄把錨點欄再複製一份 | **命中原目標**。錄製器「錨點只能出現一次」的規則本身就擋掉了——被複製的那個值會被跳過，改選只出現一次的欄位 |
| 巢狀表格，錨點落在內層 | **命中原目標**。內外兩層 tr 雖然都含那段文字，但兩條路徑最後指到**同一顆按鈕**，所以仍然唯一 |
| 錄完之後又出現一列錨點文字相同的 | **明確拒絕**（命中多筆） |

> ⚠️ 我一開始寫的是「這兩種都是真歧義、會命中多筆被擋下」——**那是錯的**。當時手寫的斷言只數了「列」的數量，
> 而重播用的是**完整的選擇器**（帶到按鈕），兩者不是同一件事。改成走真的錄製之後結論就反過來了。
> （CodeX 指出：手寫 selector 的測試不能當作錄製→重播這條路徑的驗收；他還準確預測了錨點會選到哪一欄。）

**定位與唯一性檢查在 `createRecordedLocators()`（v4.156.3）**——runner 與測試 import 同一支。
抽出來的理由跟之前 `saveRecordedScriptDoc()` 一樣：不抽的話，測試只拿得到命中數，
「這種情況應該被拒絕」變成**測試自己判的**，而 `resolveRecordedSelector()` 根本不負責拒絕。

> ⚠️ **兩條路徑的防護強度不一樣，這是既有風險（v4.156.3 釘住，尚未修）**：
>
> | 路徑 | 選擇器命中多筆時 |
> |---|---|
> | multi-TC（重錄腳本，`requireUnique: true`）| 拋「定位必須唯一」，不會點下去 |
> | 內建／自訂 TC（`requireUnique: false`）| **`.first()` 安靜取第一個**，可能不是錄製的那一顆 |
>
> `checkLocator()` 的預檢**只有 `multi-tc.js` 會呼叫**，block-engine 那條不會。
> 使用者的錄製腳本走的是 multi-TC，不受影響。

> ⚠️ **注入測試拓到的一件事**：把唯一性檢查拿掉之後，「沒有按鈕被按到」那條斷言
> **依然維持綠燈**——因為 Playwright 自己的 strict mode 會先因為解到兩個元素而拋錯。
> 所以那條驗的是「不管哪一層擋，總之不能點下去」，**不能拿它當成「唯一性檢查有效」的證據**。
> （這就是為什麼每一條防線都要分開注入：多層防護時，一條斷言的綠燈可能來自另一層。）

### 驗收標準：產品入口、實際副作用、注入會紅（跟 CodeX 定下，2026-09-17）

這一輪「看起來是防線、實際量的是一個不可能失敗的東西」出現了**五次**：

| # | 形狀 |
|---|---|
| 1 | `assert_text` 先 `.first()` 再 `count() !== 1`——「必須唯一」從寫下來就沒生效 |
| 2 | 測試逐顆 `addEventListener`，看不到 `cloneNode` 複製出來的按鈕 |
| 3 | 測試自己寫一份 strict mode 正則，把產品的防護拿掉也不會紅 |
| 4 | 兩支測試的假 page 只有 `evaluate`，驗的是產品已經不走的路徑 |
| 5 | 時序測試驗 `createRecordedLocators()`，而缺陷在 `locateRecorded()` |

所以驗收固定成三條：

1. **走產品入口**——不是測 helper，也不是測試自己再寫一份同樣的邏輯。
2. **驗實際副作用**——「有沒有按下去」看真的按鈕事件與 `page.mouse.click`，不是測試自己設的旗標。
3. **對應缺陷注入回去要真的轉紅**，而且**每一條分支分開注入**。

> ⚠️ 時序測試不能靠定時器碰運氣。要驗「click 逾時後、JS 備援前才變多筆」，
> 就包裝真實的 `click()`：等它真的逾時了才插入重複，再把原錯誤重拋。
> 用 300ms 定時器只是「大概會在那個區間」，可能因為錯的理由而綠。（CodeX 指出）

### ⚠️ 預檢與執行曾經走不同引擎（v4.157.0 修掉）

### 錄製當下就驗選擇器（v4.156.0）

| status | 意思 |
|---|---|
| `ok` | 唯一命中，而且就是剛才點的那一顆 |

**座標只當診斷資料不參與定位**——後台的座標在表格分頁、資料筆數、側欄展開、換螢幕下都會漂（H5 錄座標是因為遊戲畫在 canvas 上沒 DOM 可指）。

**錄製一定要派工給 Local Agent，不做伺服器端 fallback（v4.40.0）**：原本是在 server 的 worker process 裡 `chromium.launch({ headless: false })`——**瀏覽器開在伺服器那台的桌面上**，使用者從自己的機器連進來什麼都看不到，但 session 有起來、按鈕也變成「停止錄製（0 顆）」，看起來像成功。使用者實際回報過（2026-08-24「點了錄製沒反應」）。

Backend UAT 的執行早在 v4.23.0 就改成派工了，錄製漏掉沒跟著改。四支 WS 訊息比照 `backend_uat_*`：

| 訊息 | 方向 | 內容 |
|------|------|------|
| `backend_record_start` | server → agent | `sessionId`／`backendUrl`／`recorderScript`（原始碼，agent 端不留檔）／`marker`／`stopMarker`／帳密 |
| `backend_record_event` | agent → server | 每錄到一顆積木就即時回報一次 |
| `backend_record_stop` | server → agent | `sessionId` |
| `backend_record_done` | agent → server | `sessionId`／`error` |

**刻意不留 fallback**（跟 CodeX 討論定案）：錄製的重點就是「互動的瀏覽器要出現在操作者眼前」，退回伺服器端等於製造一個只會假成功的路徑——這次就是被它坑的。挑不到 agent 直接 409 並說明原因。

**逐顆即時回報而不是停止時一次回整包**：前端那個「已錄到 N 顆」的計數要即時才有意義（使用者靠它確認到底有沒有在錄）。server 端對未知或已結束的 session 一律忽略。

**標斷言不只有 Alt：視窗右下角有常駐的「標記模式」徽章（v4.41.0）**。Mac 鍵盤那顆鍵印的是 `option`／`⌥`，畫面寫「Alt」會讓人找不到（使用者實際問過）；而且 Mac 的 Chrome 上 Option+click 點到連結會觸發「下載連結目標」，跟標記動作打架。徽章點一下切換，開著時點任何元素都是標斷言，不依賴修飾鍵。Alt／⌥ 保留成快捷方式。

**⚠️ 注入腳本不能在最外層 `document.documentElement.appendChild(...)`**（v4.41.0 修）。這支腳本是用 `addInitScript` 注入的，跑在頁面自己的程式碼之前，那個當下 `documentElement` **還是 null**——那一行拋錯，而且因為是在最外層拋的，**後面所有標斷言的監聽器都不會被註冊**。

症狀極隱蔽：一般操作的錄製（click／change）註冊在那一行之前，照常運作、看起來錄得好好的；只有「按住 Alt 標檢查條件」完全沒反應，於是錄出來的腳本**永遠零斷言**——跑起來一定 PASS。15 項單元測試全過，完全抓不到。要掛 DOM 一律走 `mountRecorderUi()`：拿不到 root 就等 `DOMContentLoaded`。

## H5/PC 的 API 斷言（v4.164.0）

錄製時抓到的 API，點「加入檢查」就變成一顆 `assert_api_called`。上一版存 `urlPattern` 就是為了這件事。

**存的是 `urlPattern` 不是原始網址**——原始網址裡的 id／token／時間戳直接當條件，換一筆資料或隔一天重跑就全紅。

### ⚠️ 判定規則三個引擎共用一份

`assert_api_called` 會在**三個地方**被執行：

| 引擎 | 誰用 |
|---|---|
| `uat-runner/block-engine.js` | Backend（純 node 直接跑） |

| `server/routes/frontend-auto.ts` | H5/PC 伺服器端 |

「**同一條斷言，Backend 判過、H5 判不過**」，而且兩邊都不會報錯。

### ⚠️ H5/PC 的執行引擎：不認得的動作是 skipped 不是 failed

```
⏭ 不支援的動作：xxx   → skipped
```

所以**只接一個引擎等於另一個模式會安靜跳過斷言、腳本照樣 PASS**。兩個引擎都接了，

## 🚨 檢查腳本的剝註解器一直是壞的（v4.164.0 修）

所有 ui-check 都用這兩行剝註解：

```js
src.replace(/\/\*[\s\S]*?\*\//g, '').replace(/\/\/[^
]*/g, '')
```

**它在 `agent-runner.ts` 上一次刪掉 15,376 個字元、佔全檔 31% 的真實程式碼。**
原因是那支檔案裡有 XPath 字串：

```js
"//*[normalize-space(text())='Join']"
```

裡面的 `/*` 被當成區塊註解開頭，非貪婪比對一路吃到下一個 `*/`。

**後果不只是誤報**（斷言找不到東西 → 紅燈，這個還算好，看得見）。
更糟的是**反向**：要求「**不得出現某個模式**」的斷言，會因為那段程式碼被吃掉而**假通過**。

剝註解本來是為了「註解裡寫著我有做，不算做了」；結果剝的過程自己把程式碼弄丟，
**等於換一種方式得到假結論**。

改用 `scripts/ui-checks/lib/strip-comments.mjs`——認得單引號／雙引號／樣板字串／
正則字面值的小狀態機，註解換成等量空白（保留 offset，讓「A 在 B 之前」這類位置比較仍成立）。
附自我測試，XPath 那個案例就是其中一條。

**⚠️ 寫新的 ui-check 時一律 import 它，不要再自己寫那兩行正則。**

## H5/PC 錄製的 console／network／pinus 攔截（v4.163.0）

在這之前 H5/PC 錄製**什麼都不攔**：CDP 只 enable 了 `Runtime` 與 `Page`，`Network` 與 `Log` 根本沒開；收到的 `Runtime.consoleAPICalled` 只認自家兩個標記（`__TOPPATH_RECORDER__`／`__TOPPATH_CROP__`），其餘一律 `catch {}` 丟掉——連頁面自己印的 console 都收不到。

現在錄製時會一起收：

| 收什麼 | 怎麼收 |
|---|---|
| console／pageerror | `Runtime.consoleAPICalled` + `Runtime.exceptionThrown` |
| 瀏覽器層級訊息（404／CORS／mixed content） | `Log.entryAdded`（**要先 `Log.enable`**），只留 warning 以上 |
| 每筆請求 | `Network.requestWillBeSent` → `responseReceived` → `loadingFinished`，記 method／url／**urlPattern**／status／耗時／分類 |
| pinus 訊息 | 既有的 `pinusProbeSource()` 注入頁面，定期 `drainPinus()` 搬回來 |

**為什麼 pinus 這條最重要**：H5/PC 是遊戲頁，真正的業務訊息幾乎全走 pinus WebSocket，HTTP 層只看得到素材。

### ⚠️ 規則只有一份，adapter 有兩層

**執行走 Playwright、錄製走原始 CDP**——`attachNetworkCapture(page)` 吃的是 Playwright 的 `page.on()`，而錄製根本沒有 page 物件（自己開 Chrome、WebSocket 連 CDP）。所以：

- 分類／門檻／統計／上限 → `net-capture.js` 的 **`createNetCollector()`**
- pinus route 統計 → `pinus-probe.js` 的 **`pinusSummaryOf()`**
- CDP 那層只負責**把事件正規化成上面那些規則吃的形狀**（`uat-runner/cdp-capture.js`）

各寫一份的話症狀是「**同一個請求，執行時算慢、錄製時算不慢**」，而兩邊都不會報錯。

### ⚠️ 六個會靜默失敗的地方

| # | 坑 | 症狀 |
|---|---|---|
| ① | `classifyResourceType()` 沒先轉小寫 | Playwright 給 `xhr`／`image`，**CDP 給 `XHR`／`Image`**——不正規化的話全掉進 `other`，畫面上 API 永遠 0 筆、圖檔永遠 0 筆，不報錯 |
| ② | 只接一個 host | 錄製有 agent 模式（`agent-runner.ts`）與本機模式（`frontend-auto.ts`），各跑各的 CDP 迴圈。只接一邊，另一種模式面板永遠空白 |
| ③ | 計時器沒 `clearInterval` | 錄製結束後仍每 3 秒對著關掉的連線送一次，而且 session 被移除後**沒人再持有它**——agent 不重啟就永遠跑下去 |
| ④ | 沒有上限 | 遊戲一畫面上百個請求、console 也會被洗版，而這整包每 2 秒被 `/record/status` 整包回傳。agent 端與 server 端**各要擋一次**（console 是逐次 append 的） |

### 「每一列都要有」跟「第一列有就好」是不同的規格

既有 verifier 兩種寫法都有：

```js
[...rows].every(row => ...)              // 每一列（可以編輯/刪除獎池額度）
document.querySelector('...tr')          // 只看第一列（視頻可以編輯/刪除/預覽）
```

`assert_row_buttons` 的 `rows` 參數要照原本那筆的寫法選。**只做第一列的話，後面某一列缺按鈕會整個漏掉**——測試裡有一條專門守這個（第一列正常、第三列缺 Delete，`rows: 'first'` 通過、`rows: 'all'` 抓得到並指出是第 3 列）。

實測 Jackpot Ranking 那兩筆確實檢查了 50 列。

### 匯出：`doExport()` 本來就是共用的，不用「調和三支的差異」

拆匯出前的假設是「三支 verifier 各有自己的 `doExport()`，要先列差異表」。實際讀完發現**它本來就是單一函式，14 個呼叫點全部是 `await doExport(page)`、零參數、完全相同**——原作者早就避掉了「三套幾乎一樣但細節漂移」的問題。所以 `run_export` 積木也不需要參數。

**語意照原本的**：只有「Export 按鈕找不到」才算失敗；等不到下載**不是失敗條件**。唯一改動是把「等不到下載」從看起來像成功的 ✅ 改記成 `warn`——判定完全不變，但不會讓看報告的人以為檔案一定落地了。積木名稱刻意叫「執行匯出」不叫「確認下載成功」（CodeX review：不要過度承諾）。

**⚠️ 報表頁要先送出查詢，Export 按鈕才會出現。**那 6 頁在 `SUBTYPE_MAP` 裡的 action 是 `screenshot_date_search`——它會先點 `View` 或 `Search` 才交給 verifier。積木只 `open_page` 的話一定找不到匯出按鈕。所以另外做了 `submit_search` 積木，而且**`View` 跟 `Search` 兩種字都要試**：不同報表頁用的不一樣，逐頁去猜是錯的做法（原本的程式碼就是兩個都試）。

### 後台的兩個常態陷阱（拆 Reservation 時連續踩到）

**1. 站台警告彈窗的遮罩會擋住點擊。**後台登入後永遠開著一個「Currently N machines are abnormal」彈窗，它的遮罩讓 Playwright 的 `click()` 一路等到逾時。既有 verifier 全部是用 `page.evaluate(() => btn.click())` 繞過去的——那不是偶然，是這個後台的常態。`clickSelector()` 已經加上 fallback：被攔截就改用 JS 直接觸發下層元素（跟 AutoSpin／機測處理選面額遮罩同一套）。**真的找不到元素時仍然拋原本的錯，不要吞掉。**

**2. 「最後一個開著的對話框」不等於「我剛打開的那個」。**那個警告彈窗在 DOM 裡的位置不固定，`.pop()` 有時候拿到的是它。`assert_dialog_fields` 的 `scope: 'openDialog'` 改成「**在所有開著的面板裡找這顆按鈕**」——找到的那個自然就是對的面板，不用猜。

**3. 按鈕文字要精準比對優先。**`Add` 用 contains 會先命中 `Add Reservation`。既有 verifier 用的就是 `=== `，contains 只留作沒對到時的退路。

順帶：TC 描述寫的按鈕名不一定等於畫面上的。Reservation 那筆 TC 寫「+Add」，實際 `innerText` 是「Add」——**照 verifier 實際找的字，不要照 TC 描述**。

### 拆解方法：先跑基準，再比對（v4.32.0 起固定這樣做）

**不要讀完程式碼就宣稱等價。**拆解流程固定三步：① 用同一組子類型過濾跑一次**拆解前**的結果存起來（`data/raw/lark_tc_results.json` 另存成 baseline）② 寫積木 ③ 帶 `UAT_TC_STEPS` 跑同一組，逐筆比對 `pass`／`manual`／`skip`。

這套流程抓到過一個純看程式碼看不出來的 bug：引擎的 `finish()` 原本寫 `pass: criticalFails.length === 0 && !manual`，看起來很合理，但 runner 的計數是 `if (result.pass && result.manual) skipCount++`——也就是 runner 認為「manual 的那些本來就是 pass 且 manual」。引擎那個 `&& !manual` 會讓**每一筆人工判讀的 TC 都變成失敗**。只有比對基準才看得出來。

### 什麼樣的 TC 拆得動（v4.32.0 實際拆過 A 類 41 筆之後的結論）

一開始估「41 筆簡單的可以拆」，實際讀完那 9 支 verifier 之後**剩 13 筆**。差距不是估太樂觀，是分類的依據錯了——當時是照 TC 筆數和印象分的，沒讀程式碼。真正的界線是：

**8 筆本來就是 MANUAL 的不要拆**——拆完還是 manual，白做。

### 參數化模組的參數表要放比對語意，不是只放欄位名（2026-08-23 跟 CodeX 討論定案）

四支大 verifier（`verifyReportPage` 28 筆／`verifyGameSettingPage` 19／`verifyMachineReservation` 19／`verifyMeterPage` 10 = 76 筆）走參數化模組，不逐顆積木——它們有頁面流程、資料狀態、欄位組合語意，硬拆會把 verifier 的上下文切碎。

參數表**一開始就要帶比對語意**，只列欄位名稱的話，複製到另外三支時會發現不夠用、又要重拆一次：

| 欄位 | 用途 |
|------|------|
| source / target | selector 或欄位 key |
| 顯示名稱 | 錯誤訊息用（不要直接把 selector 丟給使用者看）|
| parser / normalize | 取值後怎麼正規化 |
| compare mode | `exact`／`number tolerance`／`percent`／`optional` |
| tolerance | relative／absolute，**沿用既有 `cmp()` 的規則**，不要另創一套 |
| 找不到時 | `fail`／`manual`／`skip` 三選一，要顯性宣告 |

最後一項特別重要：verifier 裡常有歷史語意、warning-only、manual fallback 這種隱性規則（這輪就踩到兩筆 note-only），不逼它顯性宣告就會在轉換時被默默改掉——而且改掉之後表面上還會看起來更「乾淨」。

### warn：查了、沒過、但不擋（v4.35.0 已實作）

引擎原本只有 pass／fail／manual 三種結果，表達不出既有 verifier 裡大量存在的 `notes.push(ok ? '✅' : '⚠️未找到')` 這種語意。少了它，轉換時只能在「當成一般斷言」跟「不拆」之間二選一——而選前者會讓 verifier 悄悄變嚴格，**且改完表面上看起來更乾淨**（多一條會擋的檢查，誰看都像改進），review 時最難抓。

`onFail: 'warn'` → 進 `warnings[]`，**不影響 pass 判定**。刻意不做「同一筆超過 N 個 warn 就升級成 fail」（跟 CodeX 討論定案）：那會變成隱性 fail，畫面顯示 PASS 卻可能被一條數量規則翻掉，規則變得不能解釋。真的需要門檻的話應該做成獨立的報表 gate。

**同一顆積木裡不同等級的失敗要能分開**：`assert_dialog_fields` 的「對話框開不起來」（功能壞了）跟「開了但少一個欄位」（可能只是規格調整）不同級，所以多一個 `onMissingFields`。這不是特例——四支大 verifier 的參數表也要能逐個比對欄位各自宣告 `fail`／`manual`／`warn`／`skip`，一顆總開關會逼人在「全都擋」跟「全都不擋」之間選，兩個都不對。

### 零斷言不得通過（v4.38.0）

**驗證器跑完但一個斷言都沒執行時，不准判定為通過。**

v4.36.1 踩過一次：`callBuiltin` 把截圖檔名當成 TC 描述文字傳給驗證器，於是每一條 `/regex/.test(full)` 都不命中、什麼都沒驗、`criticalFails` 是空的 → **綠燈**。那次是接線錯，但同樣結果還有別的成因（TC 文字被改、驗證器 regex 沒跟上、之後再接錯一次），所以要有一條跟成因無關的防線。

判斷方式（`verifierRanAssertion()`，`verifier-params.js`）：有 `criticalFails`／是 `manual`／notes 裡有 ✅❌／有非哨兵的 ⚠️ → 算有跑。**不能只認驗證器自己印的「沒有對應到已知的驗證規則」**——23 支裡只有 9 支會印。

**實際掃描結果是 0 筆**（`node server/uat-runner/scan-zero-assertion.mjs`）：121 筆裡 20 筆先被 `detectManual` 攔成人工判讀，其餘全部都對得到至少一條分支條件。所以這條防線是**防未來的迴歸**，不是在修現存的破口。

> ⚠️ v4.38.0 的 changelog 寫「掃出 19 筆」是錯的，那是掃描器自己的兩個 bug 造出來的假數字，v4.38.1 已更正：
> 1. 只認 `if (` 開頭的行，漏掉 `} else if (`——而一連串 `else if` 各接一筆 TC 正是驗證器最常見的寫法（`verifyGameSettingPage` 整支都是），虛報 11 筆

|---|---:|---|
| **會改後台資料** | 2 | Daily Ranking 的 Bonus settings（改設定＋跨 5 分鐘計時）、Set Config（把 Bonus 從 Show 切到 Hidden、Save、再切回來）|
| **要真實玩家／真實交易資料** | 6 | Gaming User ×3（要有人真的在機台內才有數字）、Jackpot Moment 的 Add ×3（Game Order 要對得到真的 Game Record）|
| **跨頁流程＋長輪詢** | 1 | Jackpot Ranking「補發後自動寫入」——要先去 Jackpot Abnormality 補發，再回來輪詢 90 秒 |
| **其他** | 3 | EGM List Showcase、GameSetting Recommend Setting、預約的 Operation Log（見下）|

**「會改後台資料」那兩筆特別不該拆**：把「改設定→存檔→改回來」包成積木，等於讓任何人組一組積木就能改後台設定。積木是給人自由組合的，能力邊界要比 verifier 保守。

**預約「操作日志」為什麼還在 builtin**：builtin 是好的，積木版打不開面板。**已排除的可能**：不是等太短（800→1400ms 一樣）、不是站台彈窗擋住（`openPath` 已補上 `dismissWarningDialog`，補完之後畫面上乾淨但面板仍沒開）。剩下的差異在「點到的是不是同一顆按鈕」——builtin 用 `querySelectorAll('button')` 精準比對 innerText，積木用 `button, .el-button, a` 先精準後包含。還沒查到底，所以維持 builtin。

> ⚠️ 這筆的過程留一個教訓：我一度從「積木失敗、builtin 通過」反推成「builtin 假通過」，還先講給使用者聽。**把 builtin 的彈窗排除邏輯補上去重跑，它照樣通過**，才發現推論反了。兩邊環境沒對齊時，不要拿比對結果去推論誰對——先確認環境一樣。


### 執行歷史（2026-08-30）

在這之前，每次跑完只寫一份 `data/raw/lark_tc_results.json`，**而且整個覆蓋**，欄位只有 recordId／subtype／task／pass／manual。沒有時間、沒有耗時、沒有失敗原因、沒有上一次。結果是這些問題全部答不出來：

- 這條 TC 是**一直**在壞，還是今天才壞？
- 這次比上次多壞了幾條？
- 這幾條失敗**是不是同一個原因**？（失敗訊息畫面上有，結果檔裡沒存）
- 哪個模組拖最久？哪條突然變慢？
- 有沒有**時好時壞**的測試？

**最後一項最要命**：不穩定的自動化測試比沒有測試更糟——它會讓人養成「紅的再跑一次就好」的習慣，然後真的壞掉那次也被當成雜訊。要偵測它一定得有逐次歷史。

**結果用 log 行送回 server，不是叫 runner 自己寫 DB**（`@@UAT_RESULTS@@` 前綴，跟 `@@UAT_STATS@@` 同一套）：派工模式下 runner 跑在別台機器上，根本碰不到 server 的資料庫；而 log 本來就會經由 `backend_uat_log` 轉回來，兩種模式共用同一條路。**前綴常數兩邊要共用**——各寫一份字串的話，改了一邊沒改另一邊的症狀是「歷史永遠是空的而且沒有任何錯誤訊息」。

| 端點 | 用途 |
|------|------|
| `GET /api/osm-uat/history` | 最近幾輪總覽，含 `failDelta`（**跟相鄰的上一輪比**，不是跟第一輪比——「這次比上次多壞幾條」才是每天實際會問的）|
| `GET /api/osm-uat/history/:runId` | 某一輪逐筆結果，含耗時與失敗原因，失敗排最前面 |
| `GET /api/osm-uat/history/flaky` | 最近 N 輪裡「有通過也有失敗」的 TC。**MANUAL／SKIP 不列入**——那不是不穩定，是本來就沒在驗。歷史不足兩輪時明講「算不出來」，不回傳空陣列假裝沒有 |

順手補的洞：TC 整筆炸掉時走 catch，**原本那裡沒有 `results.push`**——炸掉的 TC 會從結果裡消失，統計數字對不上而且事後查不到它跑過。

### 積木路徑收工前會自動截一張（2026-09-01，v4.91.0）

**積木化掉了截圖證據，而且掉了很久沒人發現。**舊的 builtin 路徑（`performAction()`）是
**無條件**先 `page.screenshot()` 再判定，所以每一筆都有截圖；拆成積木之後截圖變成
一顆要自己加的積木，而 **79 筆有積木的 TC 裡只有 3 筆加了**——其餘 76 筆的截圖證據
默默不見了。使用者問「為什麼用 agent 執行不會截圖」才發現，**跟 agent 完全無關**。

**⚠️ 拆解的驗證方法有缺口**：「拆前跑一次存基準、拆後比對」只比了 `pass`/`manual`/`skip`，
**沒有比對截圖產出**。所以當時「判定完全一致」的結論是對的，但證據少了，
而那個差異比對方法本身看不見。

**⚠️ 之後做這類等價重構，驗收條件一定要包含「外部可觀測的產出物」，不只判定結果**
（CodeX 明確列的三項）：**截圖、上傳的 payload、Lark 回寫內容**。
只比 `pass`/`manual`/`skip` 會讓「行為一致」的結論看起來成立，實際上少了東西。

修法是把「留下證據」做回 runner 行為，**不是幫 76 筆各加一顆截圖積木**——那要改 76 筆
資料，而且以後每拆一筆都要記得加，遲早再漏（跟 CodeX 討論定案）。

`finish()` 收工前補一張，四個條件：

| 條件 | 為什麼 |
|---|---|
| `explicitShots === 0` | 顯式的截圖積木代表**作者指定了證據點**，再自動加一張會破壞那個語意 |
| `!manual` | MANUAL/SKIP 本來就不上傳截圖（2026-08-07 規則），不用白截 |
| 截圖失敗只吞掉不影響判定 | 它是證據不是斷言 |
| 只截一張、就在收工前 | 見下 |

**為什麼不像 CodeX 原本設想的「失敗關鍵點 1 張 + 收工前 1 張」**：`stop` 模式（預設）
失敗時迴圈**當場 break**，所以那兩個是**同一個時間點**，分開截會得到兩張一模一樣的圖。
`continue` 模式的中途失敗刻意不額外截——那多半是預期容錯或探索步驟，每個都截會讓
Lark 附件膨脹反而更難讀。

> 已驗證 134 項（`node server/uat-runner/block-engine.test.mjs`），其中 4 項專門守這個行為：
> 沒有截圖積木時收工自動截一張｜已有截圖積木時不重複｜MANUAL 不截｜**截圖失敗不影響判定**。
>
> ⚠️ 原本有 3 項是用「截圖總數 == 0」間接證明「失敗後面的步驟沒跑」，自動截圖之後那個
> 間接證據就失效了。**改成直接看檔名**（顯式那顆叫 `never`、自動補的叫 `result`）——
> 這不是放寬斷言，是比原本更精準地斷言同一件事。

### 測試
`server/uat-runner/block-engine.test.mjs`（`node server/uat-runner/block-engine.test.mjs`），84 項，用假 ctx 不開瀏覽器。**改動執行器語意時一定要先跑它**——這裡守的是「失敗不能變成通過」那條線。

## 各 TC 對照的「解除綁定」與 Esc 關閉（2026-09-16，v4.147.0）

### 根因不是漏做刪除，是解除的入口會消失

解除綁定原本**只有一個入口**：左側候選清單的 checkbox。而候選清單
（`MultiTcRecorder.tsx:145`）長這樣：

```js
candidates = (tcScan?.url === script.larkUrl ? tcScan.tcs : tcs)
  .filter(tc => tc.source === 'live'
    && tc.storageKey.startsWith(`${script.tableId}:`)
    && `${tc.number} ${tc.text}`.includes(query))   // ← 搜尋字串
```

三個條件任一不成立，那筆已綁的 TC 就**連 checkbox 都沒有**：

| 情況 | 什麼時候會遇到 |
|---|---|
| 搜尋框有字 | 打字找下一筆要加的 TC 時，已綁的那些當場從清單消失 —— 最常踩到 |
| **重開已存腳本、Lark TC 還沒載進來** | 候選清單是空的 → **全部綁定都解不掉**（使用者實際回報的情況）|
| 那筆 TC 在 Lark 被刪或改號 | 永遠不會再出現 |

「各 TC 對照」直接畫 `script.bindings`，是**唯一永遠列全**的地方，所以解除入口放在那裡。

⚠️ **用詞是「解除綁定」不是「刪除」**（CodeX 提的）：它只從這份腳本移除，
不會動到 Lark 上的 TC。按鈕用 `is-quiet` 不用 `is-danger`，免得看起來像會刪資料。

⚠️ **checkbox 與新按鈕共用 `removeBinding()`**。各寫一份的漂移症狀是
「從 A 解除會清掉步驟歸屬、從 B 不會」，**而且兩邊都不會報錯**。

### Esc 關閉的三個條件

| 條件 | 為什麼 |
|---|---|
| `recId` 時不關 | 關掉就失去「停止錄製」的入口，而 agent 端的瀏覽器還開著 |
| **`busy` 時也不關** | 蓋住「已按下開始、還沒拿到 `recId`」與「已清掉 `recId`、還在收尾」這兩個 `recId` 為空但不該關的瞬間（CodeX 提的）|
| 未儲存要先問 | 沿用既有 `window.confirm`，與關閉鈕共用 `closeWorkbench()` |

⚠️ **未儲存判斷一定要含「還沒套用的 JSON 草稿」**：JSON 編輯框打字走的是
`setJson()`，**不經過 `edit()`、不會標記 dirty**。不納入的話 Esc 會直接把草稿丟掉。

⚠️ **解除綁定要一併清掉 `addOwner`**，否則之後「加入步驟」會綁回一個已經不存在的
`recordId`。畫面上那個 `<select>` 會退回顯示「共用」，**但值其實還在，看不出來**。

### 🚨 這輪抓到兩個「測試假綠燈」，比功能本身更該記

**1. 用 `<select>` 的 `inputValue()` 驗 `addOwner` 是假的。**
option 被移除之後，瀏覽器會讓 select **自動回報 `''`**，不管 React state 裡的值還在不在
——也就是量到的正好是那個會騙人的東西。注入違規（拿掉 `setAddOwner` 清除）時**測試照樣綠**。
改成看「加入步驟」實際寫進去的 `tcId`（存檔後從 payload 讀）才驗得到。

**2. Esc 那幾條沒先把 dirty 清掉，會「因為別的原因而通過」。**
`dirty` 一路撐著 `hasUnsaved`，於是驗 JSON 草稿、驗錄製中防線的那幾條都是被
確認對話框擋下來的，不是被要驗的那個條件擋下來的 —— **注入違規也不會變紅**。
每一條開跑前都要 `saveNow()`。

⚠️ 而 `saveNow()` 只等「儲存」的 `*` 號消失還不夠：那顆的 `disabled` 綁的是 `busy`，
而 `setDirty(false)` 發生在 `act()` 的 `finally` 之前。太早按 Esc 會被 `busy` 擋掉，
**看起來像「Esc 壞了」，其實是測試按太快**。要一併等它變回 enabled。

> 已驗證 26 項（`node scripts/ui-checks/multi-tc-unbind-esc.mjs`，需先
> `npx vite --port 5199 --strictPort`）。涵蓋 CodeX 開的四項驗收：
> 搜尋遮住 TC｜候選清單全空｜解除後儲存重開｜錄製啟停途中按 Esc。
> **已注入違規確認會變紅**：拿掉按鈕 1 紅、Esc 不擋錄製中 1 紅、
> 未儲存判斷不含 JSON 草稿 2 紅、解除不清 `addOwner` 1 紅；還原後回到 0。


### ⚠️ 「測試曾被 busy 擋住」不等於「busy 這道防線有被驗過」

CodeX review 抓到的：原本「錄製中按 Esc 不會關」紅的其實是 **`recId` 在擋**。
把 `busy` 單獨拿掉，那條**照樣綠**——等於 `busy` 從來沒被驗證過。

要驗它，必須做出「`recId` 是空的、但 `busy` 是 true」的瞬間。程式裡剛好有兩個：

| 瞬間 | 為什麼 `recId` 是空的 |
|---|---|
| **啟動中** | `act()` 已 `setBusy(true)`，但 `/record/start` 還沒回來，`setRecId` 尚未執行 |
| **停止收尾中** | `stopRecording()` 是**先** `setRecId(null)`，**才**去 `await /record/stop` |

測試把 mock 的那兩支回應卡住，就能停在那兩個瞬間按 Esc。

⚠️ **每條 Esc 斷言要各自取基準**，不要共用同一個 `before`——共用的話第一條紅掉之後
後面全部跟著紅，看不出是哪一道防線失效。

> 注入「`closeWorkbench` 只拿掉 `busy`、保留 `recId`」之後，**恰好那兩條轉紅，**
> **而「錄製中」那條維持綠** —— 這才證明它們驗的是 `busy` 不是 `recId`。
> 全套 29 項，還原後回到 0。

## 「上傳檔案」積木與集中式素材庫（2026-09-16，v4.150.0）

### 為什麼不能用錄的

點上傳鈕開的是**作業系統的原生視窗**，在瀏覽器外面。Playwright 的錄製只看得到
DOM 事件 → 錄不到；重播時那個視窗會打開然後**卡住等人選**。

改用 `setInputFiles`：直接把檔案交給頁面的 `<input type=file>`，**原生視窗不會出現**。

### 素材存 server，步驟只記 id

| 做法 | 換一台 agent 執行 |
|---|---|
| ❌ 填 agent 本機路徑 | 找不到檔——使用者一開始擔心的就是這個 |
| ✅ 素材存 DB、步驟記 id | 任何 agent 都拿得到 |

runner 用**每輪一張、跟 session 同生命週期**的取用票（`UAT_ASSET_TOKEN`）去
HTTP 取；agent 端由 `CENTRAL_URL` 推出 `UAT_ASSET_BASE`，伺服器端 fallback 指回本機。

⚠️ **素材不隨派工 payload 傳**：步驟目前整包放進 env var，20MB 檔案 base64 之後
會把環境區塊撐爆，而且同一個素材被多個步驟引用會被複製好幾份。

### ⚠️ 刻意不擋副檔名／MIME

擋了就**永遠測不了「上傳錯誤格式應該被拒絕」**，而那本來就是要測的 TC。
該擋的是受測的後台，不是這個工具（CodeX review 指出）。只限大小，單檔 20MB。

分類（影片／圖檔／CSV／文件／其他）**只用於顯示與篩選**。判斷在
`shared/uat-asset-kind.ts`，前後端共用。

⚠️ **同時看副檔名與 MIME，副檔名優先**：
- Excel 存過的 `.csv` 會回報成 `application/vnd.ms-excel`，有些系統回空字串
  → 只信 MIME 會把 CSV 標成「其他」
- 但真正的 `.xls` **也是同一個 MIME** → 那個 MIME 不能拿來判 CSV，交給副檔名

### 幾個「做錯也不會報錯」的點

| 決定 | 為什麼 |
|---|---|
