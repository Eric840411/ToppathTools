## TestCase 生成：規格書分批與 JSON 解析（2026-09-14，v4.144.0）

**規格書原本是 `docContent.slice(0, 12000)`——超出的部分靜默丟掉。**生成照樣顯示成功，
但 AI 只看過前面一段，後半的需求一條測試案例都沒有，**而且沒有任何地方查得到**。
比會報錯的那個問題更危險。

現在超過就按段落切批、逐批生成、合併。設計決定（跟 CodeX 討論定案）：

| 決定 | 為什麼 |
|---|---|
| 按段落邊界切，**不硬切字數** | 硬切會把一條需求剖成兩半，兩邊都產不出完整案例，而且產出來還很正常 |
| 批次之間**不重疊** | 重疊會產生重複案例。**重複的假案例比缺漏更難發現**——缺漏翻規格書對得出來，重複的看起來像正常資料 |
| 編號**合併後由程式重編** | 叫 prompt「你從第 N 號開始」模型會飄。重號在畫面上完全正常（每筆都有編號、格式也對），最難用肉眼抓 |
| 某批失敗**保留其他批但要明講** | 但全部失敗要丟錯——回空陣列會讓人以為「這份規格就是沒有案例」 |

🚨 **重編號一定要「依前綴分組」，不能全域套同一個前綴。**
CG_TestCase 的編號是「類型縮寫_類別縮寫_序號」（`POS_ROOM_001`／`NEG_LOBBY_003`／`BND_BAL_002`），
**前綴帶語意**。全域重編會把負面測試改寫成 `POS_ROOM_xxx`——資料被竄改，但每筆看起來格式都對。
真實資料實測：一次 2 批就出現 **12 種前綴**，全域重編會把它們壓成 1 種。

### ⚠️ 原本的 bug：fence 把截斷修復擋在門外

`extractJsonBlock` 的 fence regex 要求 ` ``` ` **成對**。回應被截斷時只有開頭沒有收尾 →
配不到 → 退到括號掃描 → 截斷內容裡沒有 `]` → **回傳原字串（fence 還在）**。
而 `repairTruncatedArray`（專門處理截斷的那層）第一行是 `if (!trimmed.startsWith('['))` →
**被 fence 擋住，等於沒作用**。

實測四種組合，**只有「fence + 截斷」會掛**，其餘三種都過。兩個各自都有處理的失敗模式，
湊在一起就沒人接得住。

⚠️ 修好之後截斷會變成「成功但少筆數」，所以走到 pass 3 一定要 `console.warn` 講明白——
**少幾筆而不自知，比直接報錯危險**。

### ⚠️ prompt 叫模型「不要包 markdown」是無效的

CG_TestCase 明寫「僅回傳純 JSON 陣列，不包含 Markdown 標記」，但 Gemini **每次都還是包
` ```json `**（實測多次皆然）。解析端本來就得自己處理 fence，不能指望 prompt。

### 診斷 log（v4.143.2 加的）

`finishReason` 原本只在 text **完全為空**時才讀，所以 MAX_TOKENS／SAFETY／RECITATION
造成的半截回應會被當成正常結果送下去，之後在 JSON.parse 才爆、而錯誤訊息只說「格式非合法」
——指錯方向。現在每次都印 `finishReason / parts 數 / token 用量`，非 STOP 或 parts > 1 另外警告。

⚠️ `gemini.ts` 三處（406/580/654）都寫 `parts?.[0]?.text`，**只取第一個 part**。
多 part 時其餘會被靜默丟掉，而且 `finishReason` 會是 `STOP`、看起來完全正常。
目前實測都只回 1 個 part，所以先加警告沒有改行為。

> 已驗證 **49 項**（`npx tsx scripts/ui-checks/spec-chunk.test.ts`）＋ **真實 Gemini 端到端**：
> 16,174 字規格書 → 切 2 批（10,782／5,390）→ 字數守恆 → 兩批都成功 →
> **重編前 30 筆撞號、重編後 0 筆**，**12 種前綴一種都沒被壓掉**。
> **已注入違規確認會變紅**：退回全域單一前綴（2 紅）、改成硬切字數（1 紅）、
> 單批失敗就整個丟錯（4 紅）、訊息不講「結果不完整」（1 紅）。
>
> ⚠️ 其中「單批失敗」那條原本是以**未捕捉例外中斷**的方式失敗，我的注入計數只數 ❌ 行，
> 會讀成 0 紅。已改成乾淨的斷言——**注入測試只看「有沒有紅」不夠，要確認紅的是預期那幾條**。

### 編號前綴可信度檢查（v4.144.1，CodeX review 提的）

**依前綴分組重編號會讓「打錯字」變成一個看起來完全正常的新系列。**
模型把 `POS_ROOM_` 打成 `POS_ROMO_` 時，重編號會把它當成獨立分組、乖乖從 001 編起——
編號格式正確、序號連續，**沒有任何地方會說那是同一組打錯字的**。

`checkPrefixConsistency()` 查三種：

| 種類 | 條件 |
|---|---|
| `type_mismatch` | 前綴第一段是 `POS` 但 `測試類型` 欄位寫「負面測試」（兩者其中一個是錯的）|
| `unknown_type` | 第一段不是 POS／NEG／BND |
| `rare_prefix` | 某前綴只出現 1 次、而其餘平均 ≥3 次（多半是打錯字打出來的）|

⚠️ **只警告、不自動改。**把 `POS_ROMO_` 改成 `POS_ROOM_` 是猜測，猜錯就是竄改資料；
而打錯字本來就該讓人看到，不是默默補好。

⚠️ **只比對第一段。**真實資料的第二段是「功能模組」縮寫而非「類別」
（ENT／BAL／DRW／PAY／CON／SYS／LOT…，一次就 12 種），模型自己發明、沒有固定集合。
硬比第二段只會產生一堆假警告，久了就沒人看警告了。

> 檢查順手把前綴「修好」（1 紅）。
>
> ⚠️ 「檢查永遠回空」那條原本只紅 1 條——因為 `issues[0].detail` 在空陣列上拋 TypeError，
