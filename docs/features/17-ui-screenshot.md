## 17. OSM Tools — UI 解析度截圖（UiScreenshotPage）

**路由**：`/api/ui-screenshot/*`

### 功能說明
從 Lark Wiki 讀取 gmid 清單，使用 Local Agent（Playwright）對 H5 遊戲進行多解析度批量截圖，結果可回寫至 Lark Wiki TABLE。

### 使用者操作
| 操作 | 說明 |
|------|------|
| 選擇客戶端（H5 / PC） | **決定掃大廳與截圖走哪條流程**：H5 讀 DOM 卡片、PC 讀 Cocos 場景樹。預設 H5 |
| 設定 Lark Wiki URL | 指定含 gmid 清單的 Wiki 文件 URL |
| 設定遊戲 URL Template | 填入含 `{gmid}` 佔位符的遊戲 URL |
| 選擇解析度 | 11 種 H5 解析度：Mobile Portrait / Landscape / Tablet，可分組全選 |
| 設定選項 | 自動關閉面額彈窗、等待推流就緒、Headed 模式、並發數 |
| 選擇 Agent | 從已連線的 Local Agent 中選擇執行裝置 |
| 開始截圖 | Agent 以 Playwright 批量執行，SSE 即時回報任務進度 |
| 停止 | 中止當前 Run，未執行任務標為 skipped |
| 查看截圖熱圖 | gmid × 解析度 Grid，截圖縮圖即時顯示，點擊放大預覽 |
| 查看清單模式 | 以表格呈現每個任務的狀態與錯誤訊息 |
| 回寫至 Lark Wiki | 將截圖結果回寫為 Wiki TABLE（每欄一種解析度）|

### ⚠️ 客戶端（H5 / PC）是使用者選的，不從網址猜

**2026-09-21 改。** 原本 agent 用 `/osm-pc|[?&]platform=pc/` 打整條網址來判平台。
問題是 **H5 的正式網址本身就帶 `&platform=pc&device=mobile`**：

```
https://osm-h5-prod.osmslot.org/?token=...&platform=pc&mode=live&...&device=mobile&...
                ↑ 主機是 H5                    ↑ 但 query 說 pc
```

於是每一次 H5 都命中 PC 分支，跑去讀根本不存在的 Cocos 場景樹，在 `pcWaitLobby` 空等 60 秒。
**畫面上只會看到 `page.waitForTimeout: Target page, context or browser has been closed`**——
完全看不出是走錯分支，看起來像網路或瀏覽器的問題。

時間線：H5 這個預設模板從 `b2bf337`（2026-05-29）就帶著 `platform=pc`；
PC 判定是 `0972ec7`（2026-09-19）才加的——加 PC 支援的當下就把既有的 H5 踩掉了。

**現在的規則：**

| | |
|---|---|
| 判定依據 | 使用者在「資料來源」卡片最上面選的 **客戶端** 欄位 |
| 傳遞路徑 | 前端 → `/scan-lobby`、`/start` 的 `clientType` → agent 的 `UiScreenshotScanMessage` / `UiScreenshotRunConfig` |
| 掃大廳與截圖 | **共用同一個值**。截圖那段整個 run 只判定一次（原本三處各判一次，其中一處還拿導頁後的 `page.url()`） |
| 選的跟主機不合 | 欄位下方黃字提醒，**不自動修正**——自動修正就是又回去猜 |
| 沒帶 `clientType`（舊版 server） | 退回看 **hostname**（`osm-pc-` 開頭 → PC），**不看 query**；而且 `console.warn` 印出來 |
| 退路遇到**未知主機** | 會當成 H5。⚠️ **這是相容限制，不是判斷結果** |

> **為什麼退路不看 query**：CodeX 的建議。`platform` / `device` 這些 query 參數在兩版之間是共用的
> （`src/data/prodSimUrl.ts` 記著「PC 不用改，只要帶域名就會自動轉換」），拿它判平台必錯。

> **不要把「沒給 clientType」默默當成 H5 或 PC** —— 那正是這個 bug 原本的形狀：安靜地跑錯分支。

> ⚠️ **不能說「已經完全沒有網址判定」**（CodeX 2026-09-21 指出）。正確的範圍是：
> **有帶 `clientType` 時才完全不看網址**。舊版 server 沒帶的那條退路仍然會看主機名，
> 未知主機還是會被當成 H5，只是多了一行 warn。可以接受作為相容限制，但不要講成沒有了。

### 驗到哪一層

這條路徑有三層，**每一層要分開驗，而且要講清楚哪一層沒驗到**：

| 層 | 驗的東西 | 怎麼驗 | 狀態 |
|---|---|---|---|
| ① 畫面 → request | 點的那個客戶端有沒有進到 request body | `scripts/ui-checks/ui-screenshot-clienttype-ui.mjs` | ✅ 8 條（`/scan-lobby` 與 `/start` 兩個入口） |
| ② request → agent | 中控有沒有原樣轉給 agent | `scripts/ui-checks/ui-screenshot-clienttype-dispatch.mjs` | ✅ 7 條 |
| ③ agent → 執行分支 | agent 收到之後有沒有真的走 DOM／Cocos | 要真大廳，只能實機跑 | ❌ **沒驗到** |

**① `ui-screenshot-clienttype-ui.mjs`**——真瀏覽器開真產品頁，點真的「客戶端」按鈕，
再分別點「掃描大廳」與「開始截圖」，攔截送出去的 `POST /scan-lobby` 與 `POST /start` 看 body。
含「再點回 H5」與「reload 後仍是 PC」（設定有存起來）。

> ⚠️ **兩個入口都要驗**（CodeX 2026-09-21 指出）。最早只攔了 `/scan-lobby`——但「開始截圖」
> 是**另一段自己組 body 的程式碼**，只驗掃描等於放掉一半。突變證實了這件事：
> 只把 `/start` 那段的 `clientType` 拿掉，**前 6 條全綠、只有 `/start` 那兩條紅**。

`/agents`、`/scan-lobby`、`/start` 的回應都是假的（`/start` 刻意回 `ok:false`，
免得前端進入「執行中」狀態、按鈕變成「停止」讓後面幾條點不到）——那些不是這支在驗的東西，當腳手架用。

**② `ui-screenshot-clienttype-dispatch.mjs`**——冒充一個 agent 接上真的 `ws://<host>/ws/agent`，
打真的 `/scan-lobby` 與 `/start`，斷言 **agent 收到的派工訊息裡的 `clientType` 就是送進去那個**。
含「H5 網址選 PC 中控不得擅自更正」「沒給不得補預設」。

**突變都驗過，而且紅的是對的那幾條：**

| 注入 | 結果 |
|---|---|
| 中控改回「網址有 `platform=pc` 就強制 pc」 | ② 的第 1、4、5 條紅（第 1 條正是這個 bug 原本的形狀），2、3、6、7 維持綠 |
| 前端 `/scan-lobby` 送出時拿掉 `clientType` | ① 的 4 條 request 斷言紅，**但兩條「畫面上選中的是 X」維持綠** |
| 前端**只有** `/start` 送出時拿掉 `clientType` | ① 的 **只有 `/start` 那兩條紅**，前 6 條全綠 |

> ⚠️ 第二個注入就是這件事的重點：**畫面渲染正確，跟送出去的值正確，是兩回事。**
> v4.251.0 當下我只截了兩張畫面圖就說驗過了——那個注入證明那樣驗根本抓不到。

### ⚠️ 彈窗：只在三個時間點關一次是不夠的

**2026-09-21 使用者回報**：進機台時跳 Confirm 彈窗沒被點掉，整個流程卡住。

查下去發現**關彈窗的功能一直都有**（`dismissUiPopups()` 會找文字剛好是
`Confirm / YES / 確定 / OK` 的按鈕，從按鈕往上爬找彈窗根節點，關到偵測不到為止），
**缺的是呼叫時機**——它只在「進機台前」「推流就緒後」「大廳模式」三個點各跑一次。

中間這三段完全沒人看，而彈窗正好都在這三段冒出來：

| 冒出來的時機 | 你看到的錯誤訊息 | 訊息有提到彈窗嗎 |
|---|---|---|
| 點卡片進場的那一下 | 「點了 (x, y) 但還停在大廳」 | ❌ |
| 等推流的迴圈 | `Game surface not ready` | ❌ |
| 截圖前等的那幾秒 | （沒有錯誤，就是拍到被蓋住的畫面） | ❌ |

**現在的做法：進機台 → 等推流 → 截圖前延遲，這一整段掛一個看門狗，每 0.7 秒看一次。**

> 🚨 **看門狗只點「已確認用途」的彈窗**（CodeX 2026-09-21）。
> 一次性關一下，跟每 0.7 秒關一次，風險不是同一件事——連續點「文字剛好是 Confirm 的按鈕」，
> 總有一天會在遊戲畫面裡點到不該點的東西，而症狀是**流程從一個沒人預期的狀態繼續跑**，
> 比卡住更難查。已確認清單在 `server/uat-runner/ui-popup.js` 的 `UI_POPUP_KNOWN`：
> 面額選單、Tips 錯誤框、純提示框。
>
> **沒見過的彈窗不點，把內容記下來跟著那張截圖一起回報**（`有彈窗未處理…`）。
> 要新增一種的條件是「實際在環境上看過，而且知道按下去的後果」，不是「看起來應該沒差」。

其他幾件一起改的：

- **`ensureUiScreenshotLobby()` 原本無條件關彈窗**，等於繞過畫面上的「自動關閉面額彈窗」開關
  （CodeX 指出）。使用者把開關關掉是想看到彈窗長什麼樣，結果這條路照樣幫他關掉。已改成吃設定。
- **截圖前一定要先把看門狗 stop 並等它跑完**，否則會拍到「正在被點掉」的那一瞬間。
- **等待期間關掉錯誤框之後，要重新確認推流就緒才算數**——直接往下走會拍到黑畫面，
  而狀態欄寫的是 `ok`。
- 整段邏輯搬到 **`server/uat-runner/ui-popup.js`**，`agent-runner.ts` 只留薄包裝。
  原本寫在 `agent-runner.ts` 裡驗證腳本碰不到，要驗就只能在測試裡再寫一份同樣的判斷，
  那等於**測試在驗自己**。⚠️ 新檔案記得加進 `AGENT_SOURCE_WHITELIST`（守門腳本會擋）。

### 驗到哪一層（彈窗）

`scripts/ui-checks/ui-popup-dismiss.mjs`——用真瀏覽器載入**重現彈窗結構的 fixture**，
呼叫**產品那一支** `dismissUiPopups()`。17 條，涵蓋 CodeX 指定的四類加反例：

| # | 情況 | 期望 |
|---|---|---|
| ① | 延遲 1 秒才出現的錯誤框 | 關得掉，而且錯誤內容有記下來 |
| ② | 面額選單 → 關掉後才跳的第二層 YES/NO | 兩層都關掉 |
| ③ | 未知 Confirm（`Daily Bonus`） | strict **不點**、回報 1 筆；非 strict 才點 |
| ④ | 「自動關閉面額彈窗」關掉時 | `ensureUiScreenshotLobby` 不得偷關 |
| 反例 | 畫面上的裸 `Confirm` 字樣（不在彈窗裡） | 兩種模式都不點 |
| 反例 | 大廳中獎彈窗 | 點 ✕，**不得點到 PLAY NOW** |

**突變逐條驗過**（每條分開注入）：

| 注入 | 紅的是哪幾條 |
|---|---|
| 拿掉 strict 的未知判斷 | ③ 那 4 條 |
| `rounds` 改成 1 | ② 那 2 條 |
| `ensureUiScreenshotLobby` 改回無條件關窗 | ④ 那 2 條 |

| ⑤ | 看門狗運作中，**另外**用非 strict 呼叫關窗 | 未知彈窗**還是點不掉** |
| ⑥ | 已經 ready 之後才冒出來的錯誤框 | 有關掉、有記成 error，上層據此重驗推流 |

> ⚠️ 第 ④、⑥b 是**讀原始碼的結構檢查**，不是行為檢查——fixture 裡沒有真的大廳。
> 真環境的行為仍需實機跑。

### ⚠️ 第一版漏掉的兩個整合情境（2026-09-21 CodeX 靜態核對抓到）

**[P1] 看門狗刻意不點的未知彈窗，被主流程點掉了。**
主流程在看門狗運作中**另外**呼叫了一次關窗，而且沒帶 `strict`（預設 `false`）。
於是 strict 等於白設，而且兩條路會同時點同一顆按鈕。

> 🚨 **修法不是「記得不要那樣呼叫」，是讓它做不到。**
> `dismissUiPopups()` 自己查 `ACTIVE_GUARDS`——這個 page 上有看門狗在跑的話，
> 不管呼叫端傳什麼，一律導進看門狗的佇列並降級成 strict。
> 靠紀律維持的不變量，遲早會有人（包括我）在別的地方再寫一次。
>
> 驗證也跟著改成「**用最容易犯錯的寫法去呼叫，也點不掉**」，而不是「檢查沒人那樣寫」。

**[P2] 「先就緒、延遲期間才出錯」不會重驗推流。**
重驗條件原本只寫 `if (!ready)`。`ready` 已經是 true、錯誤框在等截圖的那幾秒才跳出來被關掉——
**直接往下拍，拍到黑畫面而狀態欄寫 `ok`**。改成記下「期間有沒有關過錯誤框」（`sawErrorPopup`），
只要關過就一律重驗，而且錯誤訊息要講出是哪一種原因。

另外把「重新載入後已在機台內」那條快速路徑底下的等待也補上看門狗——同一個坑，只是少有人走到。

**[P3] 快速路徑也漏了同一道關卡。**（CodeX 第三次抓到，同一個 bug 的第三個住址）
我在主路徑補上「關過錯誤框就重驗」之後，**「重新載入後已在機台內」那條快速路徑照樣直接 return**——
重新載入時推流正常、延遲期間才出錯的話，一樣拍黑畫面而狀態寫 `ok`。

> 🚨 **同一條規則被寫了兩次，就一定會只修好一邊。**
> 所以這次不是「把那段也補上」，是把決策抽成純函式
> `evaluateReadyGate()`（`uat-runner/ui-popup.js`），兩條路 import 同一支。
> 副作用是**測試終於驗得到「重驗失敗不准報 ok」本身**，不必只做結構檢查——
> 這正是 CodeX 指出 ⑥／⑥b 都還沒驗到的那一格。

| ⑦ | `evaluateReadyGate` 的四種組合 | 先就緒但期間出錯 → `recheck`；重驗失敗 → `fail` |
| ⑦b | 兩條路都套了同一道關卡 | `applyReadyGate` 出現 2 處，fail 會 throw |

**突變逐條驗過**：

| 注入 | 紅的是哪幾條 |
|---|---|
| 拿掉「有看門狗就走它的佇列」 | ⑤ 那 3 條 |
| 重驗條件改回只看 `!ready` | ⑥b 1 條 |
| 主流程又在 guard 運作中補一次非 strict 呼叫 | ⑥b 的結構守衛 1 條 |
| gate 忽略 `sawErrorPopup` | ⑦ 3 條 |
| 重驗失敗照樣放行 | ⑦ 2 條 |
| 快速路徑又不套關卡 | ⑦b 1 條 |
| 失敗原因寫成含 `timeout` 的字 | ⑦ 1 條 ＋ ⑦c 1 條 |
| `prepare` 丟錯改成回報 `ok` | ⑦b 1 條 |
| 輪數上限改回 4 | ⑧ 3 條（重現真實現場） |
| 撞到上限不講話 | ⑧b 1 條 |

### 🚨 真實現場打臉：輪數上限被前面的種類吃光（2026-09-21 使用者給網址實測）

使用者給了一條實際網址，直接開來看——**這才是他回報的「Confirm 沒被點掉」的真正原因**，
跟前面猜的「呼叫時機」是兩回事（時機那個也是真的，但不是這一題）。

現場長這樣（`osm-h5-prod`、`gameid=osmbbhl`）：

| 畫面上同時有 | 數量 |
|---|---|
| `closeBtn`（整頁中獎彈窗的 ✕） | 1 |
| `notification-close`（跑馬燈中獎通知） | 4 |
| `my-dialog` → `Tips: Game exception, please contact customer service.(39)` → **Confirm** | 1 |

`rounds` 上限原本是 **4**。前 4 輪全部花在 ✕ 上，**③ Confirm 那一步一次都沒跑到**。
而回報寫的是「關掉 4 個彈窗」——**跟正常收工長得一模一樣**，完全看不出還有東西蓋著。

```
第 1 輪 關掉彈窗（✕ .closeBtn）
第 2 輪 關掉彈窗（✕ .notification-close）
第 3 輪 關掉彈窗（✕ .notification-close）
第 4 輪 關掉彈窗（✕ .notification-close）   ← 輪數用完
        → Tips (39) 的 Confirm 還在畫面上，dismissed: 4, errors: [], blocked: []
```

**改法**：上限是**安全網**不是主要限制——預設拉到 12，真正的結束條件仍是「這一輪什麼都沒關到」。
而且**撞到上限一定要 log 並記進 `blocked`**，否則又會變成無聲地少做事。

修好之後對同一條網址重跑：6 個全關掉、`(39)` 那則進了 `errors`、大廳 688 張卡片都在。

> ⚠️ 這一題**只有真環境看得到**。我前面用自製 fixture 驗的 17 條全是綠的——
> 因為我做的 fixture 每次只放一兩個彈窗，永遠不會撞到輪數上限。
> 現在 ⑧／⑧b 兩條把這個現場釘住了（4 個 ✕ ＋ 1 個 Confirm）。

### ❗ 還沒守住的一格：完整的「重驗失敗 → 任務回報 err」

CodeX 2026-09-21 指出的界線，寫在這裡免得日後誤以為驗過了：

- ⑦、⑦c 是**行為檢查**（真的呼叫 `evaluateReadyGate()`）：⑦ 驗決策回傳 `fail`，
  ⑦c 驗**它回傳的失敗原因**不含 `timeout` 字樣——原因字串取自產品那支，不是測試自己打的
- ⑦b 才是**讀原始碼的結構檢查**：兩條路都套了關卡、fail 會 throw、
  throw 會落到 `postStatus(err|timeout)`

> ⚠️ 這兩類不要混為一談（CodeX 2026-09-21 指正過一次）。把行為檢查誤記成結構檢查，
